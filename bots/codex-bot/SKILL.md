# Codex Bot

## orch jobs

Codex Bot's waiter runs `orch wait codex-bot --autostart` as Codex Bot's own user and login, under its restart supervisor (`deploy/waiter-service.sh codex-bot`, or the `orch-waiter@codex-bot` user unit), so a killed waiter comes back by itself: on each claim it starts the job itself as `orch job run codex-bot <id> --worktree -- <command>`, with the command from `~/.config/factory/waiter-codex-bot.yml` (the `codex` invocation Codex Bot chose; no job or comment text is ever added to it) and the job's standard brief, plus the repo's `factory.md` context, on the harness's stdin and in `$ORCH_JOB_BRIEF`, then goes back to waiting, so no model turn and no message from another bot is needed to start a job; `orch` never chooses a harness on its own. Each job gets exactly one handoff: once Codex Bot's autostart waiter has claimed a job, its harness run alone runs it and posts its one `orch:v1` handoff, and a Codex Bot turn never runs or posts for it. `orch` enforces this: a plain `orch wait codex-bot` is refused while the autostart waiter runs, `orch job run` and `orch job done` refuse a job that waiter claimed unless they come from its own run, a repeat `orch job done` with the same handoff is a no-op and a conflicting one is refused, and when the harness exits without `orch job done` the job goes to T6 at once. Without `--autostart`, Codex Bot runs `orch wait codex-bot --db "$ORCH_DB"` as a blocking shell call and spends no model tokens until that shell exits. The shell prints one JSON job line (`id`, `action`, `repo`, `ticket_id`, `source_comment_id`, `head`, `detail`, `attempt`, `timeout_seconds`, and the `device` the job holds a slot on, with `remote`). Codex Bot is the process that then starts the `codex` harness for that job, and it starts it as `orch job run codex-bot <id> --worktree -- codex ...`: `orch job run` sends the job's heartbeat before the harness starts and then every third of the job's `timeout_seconds`, so T6 does not time the job out, and it stops heartbeating when the harness exits, when the job is done or failed, or when `orch job run` itself dies. Do not hand-roll a heartbeat loop; `orch job heartbeat` is only for a one-off manual beat. `--worktree` runs the harness in a git worktree of one shared clone of the job's repo (its path is `$ORCH_JOB_WORKTREE`), never a fresh full clone, and removes it when the harness exits unless it has uncommitted changes or unpushed commits, which it keeps and logs. When the line says `"remote": true`, Codex Bot drops `--worktree`: `orch job run` then starts the harness on that device over Codex Bot's own SSH alias as `codex-bot`, in `$ORCH_JOB_WORKDIR` (the line's `workdir`), where the harness checks the repo out itself, and releases the device slot once the harness is confirmed gone; `orch job done` still runs on the box. When the harness has posted its `orch:v1` handoff comment, Codex Bot runs `orch job done codex-bot <id> --handoff <comment-id>`; if the job ends with no handoff, it runs `orch job done codex-bot <id> --failed` so T6 retries it.
