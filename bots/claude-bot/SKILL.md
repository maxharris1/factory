# Claude Bot

## orch jobs

Claude Bot runs `orch wait claude-bot --db "$ORCH_DB"` as a blocking shell call and spends no model tokens until that shell exits; `orch` never chooses or starts a harness on its own. The shell prints one JSON job line (`id`, `action`, `repo`, `ticket_id`, `source_comment_id`, `head`, `detail`, `attempt`, `timeout_seconds`, and the `device` the job holds a slot on, with `remote`). Claude Bot is the process that then starts the `claude` harness for that job, and it starts it as `orch job run claude-bot <id> --worktree -- claude ...`: `orch job run` sends the job's heartbeat before the harness starts and then every third of the job's `timeout_seconds`, so T6 does not time the job out, and it stops heartbeating when the harness exits, when the job is done or failed, or when `orch job run` itself dies. Do not hand-roll a heartbeat loop; `orch job heartbeat` is only for a one-off manual beat. `--worktree` runs the harness in a git worktree of one shared clone of the job's repo (its path is `$ORCH_JOB_WORKTREE`), never a fresh full clone, and removes it when the harness exits unless it has uncommitted changes or unpushed commits, which it keeps and logs. When the line says `"remote": true`, Claude Bot drops `--worktree`: `orch job run` then starts the harness on that device over Claude Bot's own SSH alias as `claude-bot`, in `$ORCH_JOB_WORKDIR` (the line's `workdir`), where the harness checks the repo out itself, and releases the device slot once the harness is confirmed gone; `orch job done` still runs on the box. When the harness has posted its `orch:v1` handoff comment, Claude Bot runs `orch job done claude-bot <id> --handoff <comment-id>`; if the job ends with no handoff, it runs `orch job done claude-bot <id> --failed` so T6 retries it.
