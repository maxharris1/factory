**The size limit.** Linear's pricing page lists file uploads as 10 MB per file on the Free plan and unlimited on Basic, Business and Enterprise. The aut0 workspace is on a paid plan: a 12.7 MiB file went through, and the `fileUpload` mutation granted a signed URL for 1.9 GiB. The connector Grok Bot used refuses sizes of 2 GB or more, so 2 GB is the only hard ceiling observed. **Build to:** no Linear-side limit below 2 GB on this workspace. #792 should still cap each video with its own setting (a factory-side choice, not Linear's), and name any file over that cap in the comment, as its scope says. If the workspace ever drops to Free, the limit becomes 10 MB per file.

**How an upload works** (Linear API docs, "How to upload a file to Linear", and what the test showed):

1. GraphQL `fileUpload(contentType, filename, size)` returns `uploadUrl`, `assetUrl` and a list of headers. `size` is the exact byte count.
2. `PUT` the raw bytes to `uploadUrl` (Google Cloud Storage) with `Content-Type`, `Cache-Control: public, max-age=31536000` and every returned header verbatim. The signed headers include `x-goog-content-length-range: N,N`, so the body must be exactly the declared size, and `Content-Disposition`. A changed or missing signed header gets HTTP 403. Upload promptly: the signed URL expired within about 60 seconds in the test.
3. Use `assetUrl` (`https://uploads.linear.app/<org>/<id>/<id>`) in a comment's Markdown, or link it to the issue as an attachment (`attachmentCreate`; the test used this path).
4. Assets are private. Reading one needs a Linear login or a signed read URL, which Linear issues for about 5 minutes. A reviewer opens them in Linear; they are not public links.
5. The `PUT` must run server-side (Linear's CSP blocks browser uploads). That fits #792: the orchestrator uploads with the Linear credential it already holds, and a lane never sees it.

Not tested: how Linear renders an inline `assetUrl` video inside comment Markdown (the test attached files to the issue). #792's build should check that once on a scratch issue.

### Form automation

- **Service.** `services/form-automation` (Node, Fastify, Playwright). Its mode is `FORM_AUTOMATION_ENV`: `development` (default; also allows localhost CORS, and with no FONN or EOB uploads keeps one random document), `remote` (local service against hosted dev data), `staging` or `production`. `config.js` refuses to start unless `SUPABASE_URL` matches the mode's project: `dpiwkypbpeepxookpjoz` for development and remote, `pbajczffxiiwhuwlveao` for staging, `corhjzoteytfszzcnawx` for production. A local `SUPABASE_URL` (`localhost`, `127.0.0.1` or `host.docker.internal`) skips that check in every mode. Hosted dev runs as Cloud Run `form-automation-dev` (us-central1, `cloudbuild-dev.yaml`, `SENTRY_ENVIRONMENT=development`).
- **Callers.** The queue worker (`supabase/functions/queue-worker/config.ts`) posts jobs to `FORM_AUTOMATION_URL` with `FORM_AUTOMATION_INTERNAL_SECRET`; unset, it logs and retries. The LLM orchestrator uses `FORM_AUTOMATION_URL`, default `http://form-automation:3000` (docker compose). The web app calls `VITE_FORM_AUTOMATION_REMOTE_URL` or `VITE_FORM_AUTOMATION_LOCAL_URL`, both in its CSP list.
- **Browser.** Local Playwright Chromium by default. `USE_BROWSERLESS=true` connects to Browserless.io instead (`production-<region>.browserless.io`, `BROWSERLESS_REGION` default `sfo`, token `BROWSERLESS_API_TOKEN`).
- **What it drives.** Each run opens its template's `target_url` from `form_templates`, unless the `/execute` request sets `inputOverrides.target_url` (`api/routes.js`). The override allows `nsa-idr.cms.gov`, `aut0.io` and `*.aut0.io`, plus `localhost`, `127.0.0.1` and plain `http:` when `NODE_ENV` is not `production`. The Docker image sets `NODE_ENV=production`; `npm run dev` leaves it unset. The seeded templates all point at the live federal IDR portal, `https://nsa-idr.cms.gov/` (`/paymentdisputes/s/`, `/entityapproval/s/`, `/paymentoffer/s/`). There is no sandbox portal and no dev-mode guard on the final "Submit Notice" step. A first run stops at a review checkpoint before submitting; the approved second run (`skipCheckpoint`) submits (`lib/automation/executor.js`). That checkpoint is an approval step, not an environment guard. `USE_TEST_VALUES` only swaps in test field values. `USE_LOCAL_AUTOMATION_FIXTURE` only loads the sections and steps of three templates from `constants/*.json` instead of the database (`lib/data/access.js`); the `target_url` stays the same. **For QA:** a lane must never reach `nsa-idr.cms.gov`. Leave it off the allowlist and run form automation only against a local page, through `inputOverrides.target_url` on a service started without `NODE_ENV=production`. The local pages are `public/idre-reselection-form.html`, `public/notice-of-offer-form.html` and `public/test-form-static.html` (served by Vite; `docs/testing/notice-of-offer-testing.md` uses `http://localhost:8080/notice-of-offer-form.html`), and `test-form/index.html`, which `test-form/test-local-form.js` opens over `file://` with its own Playwright. `supabase/templates/form-automation/test-idr-portal-form-*.json` is not a fixture: its `target_url` is the live `https://nsa-idr.cms.gov/paymentdisputes/s/`.

### Outbound email

- **Sender.** Gmail API (`gmail.googleapis.com/gmail/v1/users/<user>/messages/send`, where `<user>` is `GOOGLE_IMPERSONATED_USER_EMAIL` with the service-account key and `me` with a mailbox grant), from `CENTRAL_SENDER_EMAIL_ADDRESS` (`CENTRAL_SENDER_DISPLAY_NAME`, `RETURN_PATH_EMAIL`, `EMAIL_PRECEDENCE`, `LIST_UNSUBSCRIBE_URL`). `_shared/gmailClient.ts` `sendEmail` does the send for `outbound-email-handler`, `send-notification-email`, `send-one-time-link`, `submit-website-inquiry` and `email-template-test-sender`. The token comes from `oauth2.googleapis.com/token` through `_shared/mailboxAuth.ts`, which picks one of two ways to sign in. With none of `GOOGLE_MAILBOX_OAUTH_CLIENT_ID`, `GOOGLE_MAILBOX_OAUTH_CLIENT_SECRET` and `GOOGLE_MAILBOX_OAUTH_REFRESH_TOKEN` set, or in production, it uses the Google service-account key. Outside production, any of the three selects that mailbox's own OAuth grant; the module says dev and staging sign in that way. The web app builds case inbox addresses from `VITE_CASE_EMAIL_DOMAIN` (default `dev-mail.aut0.io`, `src/utils/caseInboxEmail.ts`), but the form runner's case alias always uses `aut0.io`. The server only logs whether `CASE_EMAIL_DOMAIN` is set.
- **Development switch.** `_shared/inbucketClient.ts` `shouldUseInbucket()` sends to local Inbucket SMTP (`INBUCKET_SMTP_HOST`, `INBUCKET_SMTP_PORT`) instead of Gmail when `USE_INBUCKET=true` or `SUPABASE_URL` contains `localhost` or `127.0.0.1`. Only then does `DEV_EMAIL_RECIPIENT_OVERRIDE` reroute every recipient to one inbox; set anywhere else it is ignored with a warning. Under `supabase start` the edge functions see `SUPABASE_URL=http://kong:8000` (`llm-gateway/index.ts` notes this), which matches neither. So **a local stack sends real mail through Gmail unless `USE_INBUCKET=true`**, and so does hosted dev.
- **Not used.** No code imports Resend; `send-notification-email/deno.jsonc` still maps `resend` in its imports. `_shared/sendgrid.ts` (SendGrid, `SENDGRID_API_KEY`) exists but nothing imports it.
- **For QA:** run aut0 locally with `USE_INBUCKET=true` set explicitly so mail lands in Inbucket, and leave the Gmail API and Google sign-in hosts (`gmail.googleapis.com`, `oauth2.googleapis.com`) off the lane allowlist.

### Payments

- **Provider.** Mercury: Accounts Receivable invoicing (`create-mercury-invoice`, `run-monthly-mercury-invoices`, `refresh-`, `reconcile-` and `download-mercury-invoice-pdf`, `mercury-webhook`, `provision-mercury-customer`) and outgoing ACH payments (`execute-ach-payment`, `reconcile-ach-payments`, `provision-mercury-recipient`). There is no Stripe code; "Stripe" appears only in docs and scraped CSS.
- **Host gate.** `_shared/mercury/environment.ts` fails closed: `MERCURY_API_BASE_URL` must be set, and a live host (`api.mercury.com` or any `*.mercury.com` but the sandbox) is allowed only in production: the first of `SENTRY_ENVIRONMENT`, `ENVIRONMENT` and `SUPABASE_ENV` that is set is `prod` or `production`, and `MERCURY_LIVE_PROJECT_REF` equals the `SUPABASE_URL` project, approved ref `corhjzoteytfszzcnawx`. Every other deployment, hosted dev included, gets `MercuryEnvironmentError` for a live host. The gate does not choose the sandbox: it uses whatever `MERCURY_API_BASE_URL` holds (hosted dev's value is a secret and was not read) and does not block a host outside `mercury.com`, such as a local mock. The sandbox base URL is `https://api-sandbox.mercury.com/api/v1` (`_shared/mercury_sandbox_env.ts`). The web app's pay link (`src/utils/mercuryPayUrl.ts`) uses `VITE_MERCURY_PAY_ORIGIN` if set, then `https://sandbox.mercury.com` if `VITE_MERCURY_API_BASE_URL` is the sandbox or `VITE_SUPABASE_URL` is local, and otherwise `https://app.mercury.com`.
- **Credentials and switches.** `MERCURY_API_TOKEN` (or `MERCURY_API_KEY`), `MERCURY_ACCOUNT_ID`, `MERCURY_WEBHOOK_SECRET`. `MERCURY_DRY_RUN=true` skips Mercury calls, but only where a dry run is allowed (`execute-ach-payment/payment_outcome.ts` `isMercuryDryRunAllowed`): a local `SUPABASE_URL` (localhost, 127.0.0.1, `kong:8000`, `.local`) or `ACH_ALLOW_PAYMENT_DRY_RUN=true`. Requested anywhere else, the call is refused rather than going live. Only `execute-ach-payment`, `provision-mercury-recipient`, `provision-mercury-customer`, `create-mercury-invoice`, `refresh-mercury-invoice` and `run-monthly-mercury-invoices` (through `create-mercury-invoice`) read it. `create-mercury-invoice` still needs `MERCURY_ACCOUNT_ID` and a valid `MERCURY_API_BASE_URL` in a dry run (it answers 503 or fails the host check without them). `reconcile-mercury-invoices`, `reconcile-ach-payments`, `download-mercury-invoice-pdf` and `mercury-webhook` ignore the flag. Without `MERCURY_API_TOKEN` (or `MERCURY_API_KEY`) the first three answer 503 and call nothing (`reconcile-ach-payments` also needs `MERCURY_ACCOUNT_ID`), and `mercury-webhook` still verifies and processes the event but skips its invoice refresh call. Sandbox integration tests read `.env.mercury.sandbox` and refuse any non-sandbox host.
- **For QA:** run aut0 locally with `MERCURY_DRY_RUN=true`, no Mercury token and `MERCURY_API_BASE_URL` set to the sandbox, or use the sandbox host only (`api-sandbox.mercury.com`, `sandbox.mercury.com`). Never allowlist `api.mercury.com` or `app.mercury.com`.
