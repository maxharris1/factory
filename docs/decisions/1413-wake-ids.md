This closes section 2 of #1413 ("Possible poller bug: a driver wake with no `job_id` or `ticket_id`").

`wake_body` in `lib/grok_delivery.py` builds one dict literal from the job row. Every key is always written, and `job_id`, `ticket_id`, `repo`, `source_comment_id` and `action` come from `NOT NULL` job columns. The Grok webhook sends those bytes as the HTTP body. The `driver: claude` fire sends the same bytes as its `text` field. The job behind the report, `083efdd8c2754be9a180e557b9c9111e` (`aut0-code/aut0`, `AUT-2286`, `clarify`, source `7105835030`), had every one of those columns set.

The reported fields were `action`, `attempt`, `detail` and `timestamp_ms`. `wake_body` has no `timestamp_ms`. The only `timestamp_ms` is the receiving side's webhook envelope (`headers`, `body_digest`, `body`, `timestamp_ms`), which carries the poller's whole body as a string in `body`. So the report read the envelope, or a partial view of it, instead of parsing `body`. Two more things made the job hard to find. `driver_inbox` was empty because `orch.yml` has no `driver_inbox:` key, so no inbox row is written. Aut0 tickets are keyed by Linear id (`AUT-2286`), so a lookup of PR number 1360 finds nothing.

`tests/test_wake_payload.py::test_a_linear_keyed_clarify_wake_carries_every_id` pins the ids for that job's shape in both the wake body and the Claude fire text. Each successful webhook delivery writes one `orch poll:` line, `wake delivered: job=<id> repo=<repo> ticket=<id> action=<action> attempt=<n> body_sha256=<hex>`. The hash covers the wake body bytes, which are the Grok HTTP body and the Claude fire's `text`. The line carries no URL, key or token. A failed delivery writes no such line, and an inbox-only route already records the job id in its `driver_inbox` row.
