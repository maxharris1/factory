# QA lane 1 brief

You are QA lane 1 for pull request #42. This brief is the whole hand-off. Nobody will message you while you run, and no skill needs to be installed. The factory's router `skills/factory/factory-qa/SKILL.md` documents this procedure, and this brief carries it in full. Work through the sections in order.

This lane checks that pull request #42 meets the acceptance criteria its scenarios cover, at the pull request's head commit. It owns these scenarios:

- s-1, for ac-1
- s-2, for ac-2

This lane owns no other scenario.

## Boot
Run the boot command, from factory.md on the base branch, in the second worktree:

````
bash scripts/qa/boot-lane.sh
````

Wait until it reports ready. Record the boot time in seconds, from the start of the command to ready, as `boot_seconds`. A boot that never reports ready is a failed health check.

## Health check
Run each doctor command in the second worktree. Every one must succeed:

````
bash scripts/qa/doctor.sh
curl --fail http://127.0.0.1:8080/health
````

Run the health check before the first scenario and again after any scenario fails. Never drive an instance that has not passed its health check.

If the health check fails, run the recover command once:

````
bash scripts/qa/recover.sh
````

Then run the health check again. If it still fails, stop and report `BLOCKED` with its output. A boot that never reports ready, or a health check that still fails, is never a failed scenario. Drive no further scenario, and mark each scenario not yet run `inconclusive`. Record the last health check result in `doctor`.

## Driving
Give input only through the UI at `http://127.0.0.1:8080`. Clicks, typing and navigation in the browser are input. Nothing else is.

factory.md names no verify skill, so use the fallback below.

The fallback. If the second worktree has its own Playwright (a `playwright.config.*` file, or `@playwright/test` in `package.json`), drive with it and write `"method": "fallback-playwright"` in the result. Otherwise use the `control-ui` recipe and write `"method": "fallback-control-ui"`. The `control-ui` recipe has four steps. Open `http://127.0.0.1:8080` in a headless browser by a script. Give input only by clicks and typing. Wait for the network to go idle after each step. Then take a screenshot. Install a browser library in a scratch folder outside both checkouts if the machine has none. Having no skill is never a reason to stop.

Database reads and log reads are allowed as read-only diagnostics only, never as input. The read-only diagnostics are:

- reading the app's logs and the boot command's output;
- a database query that reads and changes nothing.

Never write to the database, call the app's API directly, or change a file to make a scenario pass.

Give each failed scenario a `cause`. It is `product` when the app does not do what the criterion says. It is `drift` when the app does what the criterion says, but the verify skill's steps, selectors or feature map no longer match it. Only a lane whose method is the verify skill may report `drift`. Under a fallback method every failure is `product`. Give a scenario that did not fail no `cause`.

## One repeat
A failing scenario may be repeated once, never more. Report it as "failed 2 of 2" when the repeat fails too, or "failed 1 of 2" when the repeat passes. Both are failures. Record the number of repeats in `repeats`.

## Blocking bar
A finding is `[blocking]` only when the scenario's pass test fails at the commit under test, with a saved artifact that shows it, and the bug is on a path the change touched or is an unmet criterion. Everything else is `[follow-up]`. Report every issue you can show, not only the first.

## What cannot be driven
A scenario that needs a real email, a payment, an SMS, an outside sign-in or a performance measurement needs a human check. Do not drive it. Mark its result `needs-human` and say what a person must check. The lane still reports on the rest.

## Evidence
Save every artifact under `/tmp/swarm-42/worker-1/<flow-id>/`, where the flow id is the scenario id, for example `/tmp/swarm-42/worker-1/s-1/`. Name each file as the scenario's `save` list does. Each scenario saves `after-screenshot.png`, a screenshot of the page after its last step, and `pass-test-output.txt`, the text of what its pass test observed. Wait for the page to settle, with the network idle and no animation running, before a screenshot. Record a video of each scenario that has more than one step. Save a browser trace of each scenario that fails. Never delete evidence during cleanup.
